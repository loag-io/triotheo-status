# TrioTheo status

The public status page for [triotheo.com](https://triotheo.com), and the monitor behind it.

**Why it lives here and not on the site.** A status page hosted on the server it reports on goes dark
with the server. This one is served by GitHub Pages from this repository and fed by GitHub's runners,
so it keeps answering when the box does not. On 2026-10-16 the production VPS was powered off by its
host for ten minutes and nobody would have known — the outage was seen only because a deploy check
happened to be running. This repository is the answer to that.

## How it works

- **`check.py`** runs every ten minutes on a GitHub Actions schedule (`.github/workflows/uptime.yml`)
  and probes four things: the site, the API's health route, **one lesson manifest** (because the site
  can be up while the lessons readers are served are stale — the manifest must come back as JSON,
  not the app's HTML fallback), and the beta host. Standard library only.
- It writes **`status.json`** (the latest verdict), **`history.json`** (one entry per check, kept 30
  days — the uptime tubes) and **`incidents.json`** (every down→up transition with its duration), and
  commits them. **`index.html`** reads those three files and draws the page.
- **Two rules keep it honest and quiet.** A probe is retried three times before it counts as failed
  in a run, and a service is called *down* only when it failed on two consecutive runs — GitHub's
  runners are intermittently blocked at the host's edge, and one unlucky run is not an outage. A
  recovery is reported at once.
- **When a service changes state** the workflow posts one line to Discord through the `DISCORD_WEBHOOK`
  secret: `🔴 Learn lessons is down — no answer on two checks in a row`, then `🟢 … is back after about
  12 min`. Nothing is posted while nothing changes.

## Setting it up (once)

1. Create this repository **public** (Pages and Actions minutes are free there; nothing in it is
   private — it holds probe results).
2. *Settings → Pages*: deploy from branch `main`, folder `/ (root)`.
3. *Settings → Secrets → Actions*: add `DISCORD_WEBHOOK` (the same webhook the deploy notices use).
4. Optionally a custom domain: a `CNAME` file holding `status.triotheo.com` and a CNAME record at the
   registrar pointing `status` at `<owner>.github.io`. Until then the page is at
   `https://<owner>.github.io/<repo>/`.
5. *Actions → uptime → Run workflow* once to seed the data.
6. **The ten-minute trigger.** GitHub's own `schedule` is best-effort and on this repository never fired, so the
   cadence comes from a free [cron-job.org](https://cron-job.org) job that POSTs the workflow's dispatch endpoint
   every ten minutes — `https://api.github.com/repos/loag-io/triotheo-status/actions/workflows/uptime.yml/dispatches`,
   body `{"ref":"main"}`, headers `Accept: application/vnd.github+json`, `X-GitHub-Api-Version: 2022-11-28`,
   `Content-Type: application/json` and `Authorization: Bearer <token>`. The token is a **fine-grained** personal
   access token with access to **only this repository** and **only Actions: read and write**; it lives in the job
   and nowhere else. A good call answers `204`; cron-job.org emails on a failure (an expired token shows up there
   first). The workflow keeps an hourly `schedule` as a fallback. **Rotate the token before it expires.**

## Adding a probe

One line in `SERVICES` in `check.py`: an id, a name, a URL, and what must be true of the answer
(status code, and optionally a content type the reply must carry). The page picks it up from
`status.json` — no change to `index.html`.

## The page

`index.html` is generated by `build_page.py` from the TrioTheo design system — Trioscript (SIL OFL 1.1,
see `OFL.txt`), the Learn app's colour tokens, and the hand-drawn pen ported verbatim from the owner
dashboard. It is a single self-contained file with no external requests except the three JSON files
beside it. Regenerate it after a design change; never edit it by hand.
